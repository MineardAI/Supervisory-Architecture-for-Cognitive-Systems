Contract 007 — Controller

Section 4 — Controller State and Memory

4.1 Purpose

This section defines the canonical representation, lifecycle, authority, and conformance requirements for persistent mathematical state used by Contract 007.

Controller State exists to support deterministic stateful control while preserving the SACS requirements for:

* committed inputs;
* immutable artifacts;
* deterministic replay;
* explicit lineage;
* cycle isolation;
* reduced-authority failure;
* prohibition of hidden runtime authority.

Its defining rule is:

Every value from a prior controller evaluation that may influence a future canonical Control Command SHALL exist in an immutable, cycle-bound Committed Controller State artifact.

Hidden mutable Controller State is prohibited.

⸻

4.2 Controller State Identity

Controller State is the persistent mathematical memory legally available to a Controller Composition during one supervisory cycle.

Controller State MAY include:

* accumulated error;
* prior error;
* prior derivative estimates;
* prior controller output;
* integrator state;
* observer state owned by the controller;
* adaptive parameters;
* adaptive covariance;
* optimization warm-start state;
* composition arbitration state;
* fallback activation state;
* controller dwell counters;
* controller-local timers;
* finite-state controller mode;
* constraint-activation history;
* registered numerical solver state.

Controller State SHALL contain only information required for deterministic control computation.

Controller State SHALL NOT contain:

* raw observations;
* estimator internals;
* hidden OSV reconstruction;
* uncommitted governance information;
* uncommitted objective information;
* inferred supervisory intent;
* execution instructions;
* task content;
* undocumented runtime memory.

⸻

Contract 007 owns:

* Controller State semantics;
* Controller State Definitions;
* Controller State schemas;
* state initialization rules;
* state validity rules;
* state transition evaluation;
* state reset semantics;
* state partitioning within compositions;
* state lineage;
* proposed next-state construction;
* committed next-state artifacts;
* Controller State conformance;
* prohibition of hidden mutable state.

Contract 007 does not own:

* supervised-system state;
* OSV state;
* estimator state;
* governance state;
* objective persistence;
* Operational Profile transition state;
* inference-runtime state;
* execution-system state.

Controller State SHALL remain distinct from all upstream and downstream state artifacts.

4.5 Stateful and Stateless Controllers

A Controller Definition SHALL declare one memory class:

STATELESS
STATEFUL

A stateless controller:

* does not require persistent controller memory;
* SHALL produce identical output from identical current-cycle committed inputs;
* MAY use temporary local values that do not survive the evaluation;
* SHALL NOT allow temporary values to affect a later cycle.

A stateful controller:

* requires a Committed Controller State;
* SHALL identify its required State Definition;
* SHALL consume exactly the committed state authorized for the current cycle;
* SHALL produce a proposed next Controller State when evaluation succeeds or when its registered failure policy requires one.

A controller SHALL NOT be treated as stateless merely because its persistent memory is stored inside an implementation process.

4.7 Cycle Binding

Every Committed Controller State SHALL identify the cycle for which it is an authorized input.

A state committed as the result of cycle (t) normally becomes effective for cycle (t+1).

Conceptually:

[
z_t
\longrightarrow
\mathcal{K}t
\longrightarrow
\widetilde z{t+1}
\longrightarrow
\operatorname{Commit}
\longrightarrow
z_{t+1}
]

where:

* (z_t) is the Committed Controller State consumed during cycle (t);
* (\widetilde z_{t+1}) is the Proposed Controller State produced during evaluation;
* (z_{t+1}) is the immutable Controller State committed for the next authorized cycle.

A Controller Composition SHALL NOT mutate (z_t).

⸻

4.8 Canonical Stateful Computation

A stateful Controller Composition SHALL be modeled as a deterministic state transition:

[
\left(
u_t,
\widetilde z_{t+1}
\right)

\mathcal{K}
\left(
\varepsilon_t,
X_t^{\mathrm{OSV}},
R_t,
\mathcal{G}_t,
\Theta_t,
C_t,
z_t
\right)
]

where:

* (\varepsilon_t) is the Committed Control Error;
* (X_t^{\mathrm{OSV}}) is the Committed OSV when explicitly required by the registered controller interface;
* (R_t) is the Committed Reference State when explicitly required;
* (\mathcal{G}_t) is the Committed Governance Snapshot or its authorized mathematical projection;
* (\Theta_t) is the Committed Controller Configuration;
* (C_t) is the Committed Control Constraint Set;
* (z_t) is the Committed Controller State;
* (u_t) is the proposed bounded control output;
* (\widetilde z_{t+1}) is the Proposed Controller State.

A conforming implementation SHALL produce identical (u_t) and (\widetilde z_{t+1}) from identical canonical inputs, subject to the declared Numeric Profile.

⸻

4.10 Controller State Commitment

Controller State commitment SHALL be atomic.

Before commitment, proposed state is noncanonical.

After commitment:

* the state vector is fixed;
* its schema is fixed;
* its effective cycle is fixed;
* its configuration binding is fixed;
* its composition binding is fixed;
* its prior-state reference is fixed;
* its prior-command references are fixed;
* its Numeric Profile is fixed;
* its provenance is fixed;
* its artifact hash is fixed.

A correction SHALL create a new artifact with explicit supersession lineage.

A committed state SHALL never be edited in place.

4.12 First-Cycle Initialization

* a valid prior Committed Controller State; or

4.14 Invalid-State Failure

When required Controller State is unavailable, invalid, incompatible, stale beyond its permitted age, or fails integrity validation, Contract 007 SHALL NOT permit hidden reconstruction.

The registered failure policy MAY require:

INITIALIZE_RESTRICTED_STATE
RESET_STATE
ACTIVATE_REGISTERED_FALLBACK
PRODUCE_ZERO_CORRECTION
PRODUCE_RESTRICTED_CORRECTION
WITHHOLD_CONTROL_COMMAND
TERMINATE_CONTROLLER_EVALUATION

Failure handling SHALL satisfy Controller Failure Monotonicity.

State failure SHALL NOT produce:

* expanded gains;
* relaxed limits;
* increased authority;
* an unregistered controller;
* an undocumented default state;
* reuse of invalid state as nominal.

4.19 Controller-Local State

Controller-local state SHALL be readable and transitionable only by its owning controller instance unless a registered composition policy explicitly permits another component to consume it.

A controller instance SHALL NOT modify another instance’s state directly.

Cross-instance effects SHALL occur only through:

* committed composition inputs;
* registered arbitration results;
* registered shared-state transitions;
* explicit state-transition operators.

⸻

4.20 Shared Composition State

Shared composition state MAY be used when multiple controller instances require common deterministic memory.

Shared state SHALL:

* have a registered definition;
* have explicit read and transition authorities;
* use deterministic conflict resolution;
* be committed atomically with the composition’s next state;
* preserve full contribution provenance.

Parallel branches SHALL NOT race to mutate shared state.

Physical concurrency SHALL NOT affect canonical results.

⸻

4.23 Evaluation Order

Contract 007 SHALL use the terms:

controller evaluation order
composition evaluation order
operator precedence

Contract 007 SHALL NOT use “controller execution order” to describe mathematical evaluation.

Runtime execution authority belongs downstream.

Evaluation order SHALL be deterministic and registered.

⸻

4.24 Parallel Evaluation Semantics

Parallel controller branches SHALL be logically independent evaluations over identical committed inputs unless a registered topology explicitly defines differing branch inputs.

Physical simultaneity is not required.

Implementations MAY evaluate branches:

* concurrently;
* sequentially;
* through distributed deterministic workers.

Scheduling differences SHALL NOT change the canonical result.

⸻

4.28 Rate-Limit Baseline Invariant

Every rate-limiting rule SHALL declare exactly one canonical baseline semantic.

A conforming implementation SHALL NOT substitute:

* previous computed command for previous applied command;
* previous accepted command for previous applied command;
* internal actuator state for a canonical receipt;
* undocumented local memory for a committed artifact.

If the required baseline is unavailable, the registered reduced-authority failure policy SHALL apply.

⸻

4.29 Adaptive Controller State

Adaptive controllers MAY maintain:

* parameter estimates;
* adaptation gains;
* parameter covariance;
* confidence state;
* bounded learning accumulators;
* model coefficients;
* registered adaptation history.

All adaptation state capable of affecting canonical output SHALL be included in Committed Controller State.

Adaptation SHALL NOT:

* modify Governance;
* modify the Operational Profile;
* replace the committed Controller Configuration;
* broaden Controller authority;
* alter unregistered algorithm structure;
* learn from noncanonical hidden inputs.

Adaptive state updates SHALL remain bounded by registered adaptation constraints.

⸻

4.30 MPC and Solver State

An MPC or optimization-based controller MAY use:

* prior solution trajectories;
* active-set state;
* dual variables;
* primal warm starts;
* solver continuation state;
* horizon-local cached matrices.

Such state MAY be canonical only when it can affect the resulting Control Command.

Warm-start information that affects only performance and provably cannot affect the canonical result MAY remain noncanonical implementation-local cache.

When warm-start state may affect convergence, selected optimum, termination, or numeric output, it SHALL be included in Committed Controller State.

⸻

4.31 Canonical State Versus Noncanonical Cache

An implementation MAY maintain noncanonical caches only when those caches cannot alter:

* the canonical Control Error;
* the canonical Control Command;
* the proposed next Controller State;
* the Authority Certificate;
* failure disposition;
* deterministic replay.

The burden of proof belongs to the implementation.

Any value capable of affecting canonical output SHALL be canonicalized as Controller State.

⸻

4.34 State Commitment and Command Failure

A Proposed Controller State SHALL NOT be committed as nominal future state when its associated Control Command fails canonical commitment, unless a registered failure-transition policy explicitly permits the state transition.

Examples of permitted failure transitions MAY include:

* incrementing a deterministic failure counter;
* activating registered fallback state;
* clearing an invalid warm start;
* recording safety-controller activation;
* resetting an integrator after saturation.

Failure-transition state SHALL remain reduced-authority and fully traceable.

4.36 Controller Failure Monotonicity

Controller failure SHALL NOT produce greater supervisory authority than successful computation.

Formally, if (A_{\mathrm{success}}) is the maximum authority available under successful controller evaluation and (A_{\mathrm{failure}}) is the authority resulting from failure handling, then:

[
A_{\mathrm{failure}}
\preceq
A_{\mathrm{success}}
]

Failure SHALL NOT result in:

* expanded control bounds;
* higher gains;
* relaxed rate limits;
* removed saturation;
* wider action spaces;
* increased execution permission;
* activation of an unregistered controller;
* undocumented state restoration.

⸻

4.37 Hidden Mutable State Prohibition

A conforming Contract 007 implementation SHALL NOT use hidden mutable state capable of affecting canonical output.

Prohibited hidden state includes:

* process-local integrator values;
* undocumented prior-error storage;
* unregistered adaptive parameters;
* hidden fallback counters;
* runtime-only dwell counters;
* undocumented solver warm starts;
* mutable singleton controller memory;
* host-specific persisted values;
* undeclared random generator state.

The presence of hidden output-affecting state is a conformance failure.

⸻

4.40 Controller State Invariants

Every conforming implementation SHALL preserve the following invariants.

Explicit Memory

Any prior value capable of affecting a future canonical Control Command SHALL be represented in Controller State.

Immutability

Committed Controller State SHALL never mutate.

Cycle Isolation

Controller State SHALL be authorized for exactly one effective supervisory cycle.

Functional Evaluation

Controller evaluation SHALL be purely functional with respect to all committed inputs, including Controller State.

State Separation

Controller State SHALL remain distinct from OSV, estimator state, Profile state, and execution state.

No Hidden Reconstruction

Missing Controller State SHALL not be reconstructed from noncanonical history.

Deterministic Transition

Identical canonical inputs SHALL produce identical proposed next state.

Authority Preservation

State initialization, transition, migration, reset, and failure SHALL not expand supervisory authority.

Composition Ownership

Every state component SHALL have one declared owner and one registered transition authority.

Replayability

Independent conforming implementations SHALL be able to replay the state transition from canonical artifacts.

Amendment I — Configuration Ownership

Contract 007 owns:

* Controller Definition semantics;
* Controller Configuration semantics;
* Controller Configuration schema;
* Controller Configuration conformance.

Contract 006 selects and commits the controller-related profile references required for the cycle, including:

* Controller Definition reference;
* gain schedule reference;
* Numeric Profile reference;
* constraint profile reference;
* composition profile reference.

Contract 007 SHALL perform a deterministic Controller Configuration Binding operation that materializes those references into one Committed Controller Configuration.

The binding operation SHALL NOT select alternatives or reinterpret the Operational Profile.

Its only authority is deterministic materialization and compatibility validation.

Amendment K — Evaluation Failure Companion

Exactly one canonical Control Command SHALL exist for every successful controller evaluation.

An unsuccessful controller evaluation SHALL:

* produce no canonical Control Command; and
* produce exactly one Controller Failure Artifact or canonical incomplete-cycle disposition.

No ambiguous partial command SHALL cross the Contract 007 output boundary.
