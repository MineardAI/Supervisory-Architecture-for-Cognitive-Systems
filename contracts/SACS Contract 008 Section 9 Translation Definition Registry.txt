9. Translation Definition Registry

9.1 Purpose

This section defines the immutable Translation Definition Registry used by Contract 008 to map canonical Control Command semantics into runtime-specific Inference Command representations.

A Translation Definition specifies how one declared supervisory meaning may be represented for one declared runtime capability model.

It does not decide:

* whether the Control Command should exist;
* whether the command is authorized;
* whether another command would be preferable;
* whether another runtime should be selected;
* whether an approximate command is acceptable;
* whether execution should proceed.

Its sole purpose is to answer:

Which exact registered transformation preserves this Control Command’s meaning, restrictions, authority, scope, ordering, atomicity, and numeric obligations for this declared runtime?

The Translation Definition Registry SHALL make every permitted translation transformation explicit, versioned, hash-addressable, deterministic, and independently reviewable.

⸻

9.2 Architectural Identity

The Translation Definition Registry is a reusable definition system.

It contains immutable rules that connect:

Control Command semantics
        ↓
Translation requirements
        ↓
Runtime capability assumptions
        ↓
Inference Command representation

A Translation Definition is not:

* a Control Command;
* an Inference Command;
* a Translation Configuration;
* a runtime selection;
* a capability declaration;
* a governance rule;
* a fallback decision;
* an execution policy;
* an adapter implementation;
* a verification verdict.

A Translation Definition describes a permissible semantic-preserving transformation.

It does not authorize itself for use.

⸻

9.3 Registry Authority

The Translation Definition Registry owns definitions for:

* source Control Command Type compatibility;
* source semantic-class compatibility;
* target Inference Command Type compatibility;
* runtime capability prerequisites;
* parameter mappings;
* unit conversions;
* enum mappings;
* field mappings;
* deterministic derivations;
* semantic decomposition;
* semantic composition where expressly permitted;
* ordering transformations;
* atomicity preservation mechanisms;
* transaction representation;
* compensation representation;
* failure-semantics representation;
* target and scope preservation;
* expiry representation;
* cardinality preservation;
* authority-expression preservation;
* restriction-preservation rules;
* equivalence-validation obligations;
* proof obligations;
* canonical serialization requirements;
* registered translation failure conditions.

The registry does not own:

* command selection;
* runtime selection;
* provider selection;
* model selection;
* translation-profile selection;
* capability-profile commitment;
* execution dispatch;
* retry behavior;
* live runtime adaptation;
* approximate fallback;
* supervisory intent.

⸻

* parameters appear related;
* provider documentation uses similar terminology;
* the implementation considers the mapping intuitive;
* a prior version supported a similar command.

Source semantic identity SHALL be proven through exact registered bindings.

⸻

9.8 Translation Definition Selection Authority

Translation Definition selection SHALL be constrained by the Committed Translation Configuration.

Contract 008 MAY select one Translation Definition only from the set explicitly authorized by that configuration.

Selection SHALL additionally require:

* source command compatibility;
* runtime capability compatibility;
* runtime-version compatibility;
* adapter-version compatibility;
* numeric-profile compatibility;
* registry-version compatibility;
* semantic-requirement compatibility;
* absence of applicable exclusions.

Contract 008 SHALL NOT:

* search outside the committed authorized definition set;
* prefer a definition because it is easier;
* select a definition because it is cheaper;
* select a definition because it is faster;
* select a definition because another definition failed;
* select an approximate definition;
* synthesize a missing definition.

If no authorized compatible definition exists, translation SHALL fail.

⸻

9.9 Definition Specificity

When multiple authorized Translation Definitions are compatible, the selection rule SHALL be deterministic.

Specificity MAY be ordered by:

1. exact runtime target;
2. exact runtime version;
3. exact adapter version;
4. exact Control Command Type;
5. exact semantic class;
6. exact parameter-domain match;
7. exact Translation Profile;
8. declared precedence rank;
9. canonical definition identifier ordering.

The precedence model SHALL be defined by the Committed Translation Configuration or an exact referenced registry definition.

Implementation preference SHALL NOT determine selection.

Ambiguous selection SHALL produce failure.

⸻

9.11 Identity Mapping

An identity mapping preserves both value and semantic role.

For:

p_{\mathrm{runtime}}
=
p_{\mathrm{control}}

identity requires:

* identical semantic meaning;
* compatible numeric representation;
* compatible unit;
* compatible scope;
* compatible temporal meaning;
* compatible interaction semantics.

Equal numeric values do not by themselves establish identity.

For example:

temperature = 0.4

may have different semantics across runtimes if parameter scales or sampling behavior differ.

Identity SHALL be semantic, not merely syntactic.

⸻

9.16 Semantic Decomposition Rules

* compatible with runtime capability.

Partial decomposition is prohibited unless the source definition explicitly allows optional members.

⸻

9.17 Semantic Composition Rules

A Semantic Composition Rule permits several source requirements from one Control Command to be represented by one runtime instruction.

Composition SHALL be permitted only when the single runtime instruction preserves all source requirements.

9.19 Target Preservation Rules

Target-preservation rules SHALL define:

* source target identity;
* target runtime identity;
* identifier transformation;
* namespace mapping;
* alias resolution;
* uniqueness requirements;
* target-validation requirements.

A Translation Definition SHALL NOT permit target substitution.

An unavailable target SHALL cause failure.

A target alias SHALL be permitted only when the alias mapping is immutable and proves identity.

⸻

9.20 Temporal Preservation Rules

A Translation Definition SHALL specify how temporal semantics are preserved.

It SHALL define mappings for:

* effective time;
* duration;
* expiry;
* request-bound validity;
* session-bound validity;
* reversal conditions;
* deadline behavior.

Temporal mapping SHALL distinguish:

* native runtime enforcement;
* adapter enforcement;
* Contract 009 gate enforcement.

These enforcement models SHALL NOT be treated as equivalent unless the Translation Definition proves equivalence for the source requirement.

⸻

⸻

9.22 Cardinality Preservation Rules

A cardinality-preservation rule SHALL specify how source action and target counts correspond.

It SHALL distinguish:

* instruction count;
* semantic-action count;
* target count;
* transaction count;
* application count.

One source action MAY require several target instructions.

That does not grant authority for several independent applications.

The rule SHALL prove that decomposition does not multiply authority.

⸻

9.25 Transaction Preservation Rules

A transaction-preservation rule SHALL map:

* begin semantics;
* member inclusion;
* commit semantics;
* rollback semantics;
* isolation;
* visibility;
* timeout;
* failure propagation;
* compensation.

A runtime sequence SHALL not be labeled transactional without a registered transactional capability.

Contract 009 SHALL receive explicit transaction semantics.

It SHALL not infer them.

9.27 Failure-Semantics Rules

A Translation Definition SHALL state how source failure requirements are represented.

Failure rules SHALL distinguish:

* rejection before application;
* partial application;
* rollback;
* compensation;
* unknown application state;
* acknowledgement failure;
* timeout;
* target change;
* expiry.

A runtime that cannot express the required failure semantics SHALL be incompatible.

A Translation Definition SHALL NOT convert fail-closed semantics into best effort.

9.30 Semantic Equivalence Rules

Each Translation Definition SHALL specify a semantic-equivalence rule.

Let:

R_t

be the Translation Requirement Set, and:

I_t^{*}

be the Proposed Inference Command Set.

The definition SHALL establish:

I_t^{*}
\models R_t

where satisfaction means that every mandatory requirement is explicitly represented and no prohibited effect is introduced.

The equivalence rule SHALL define:

* positive-effect preservation;
* restriction preservation;
* prohibition preservation;
* target preservation;
* scope preservation;
* temporal preservation;
* cardinality preservation;
* ordering preservation;
* atomicity preservation;
* transaction preservation;
* numeric preservation;
* authority non-expansion.

9.32 Translation Definition Exclusions

A Translation Definition SHALL list known conditions under which it must not be used.

Exclusions MAY include:

* unsupported source parameter range;
* unsupported runtime version;
* unsupported scope;
* unsupported target type;
* unsupported composite interaction;
* unavailable atomicity;
* incompatible numeric profile;
* insufficient expiry mechanism;
* prohibited adapter behavior;
* ambiguous provider semantics.

An applicable exclusion SHALL make the definition ineligible.

Contract 008 SHALL NOT override an exclusion.

⸻

9.33 Fallback Definitions

A Translation Definition MAY identify an alternative representation only when that alternative is itself independently registered as translation-equivalent.

Such an alternative SHALL NOT be called a fallback unless it preserves the exact same supervisory meaning.

A registered equivalent alternative MAY be used only when:

* the Committed Translation Configuration authorizes it;
* deterministic precedence permits it;
* runtime capability supports it;
* all proof obligations pass.

A weaker action, safer action, cheaper action, or more available action is not a translation fallback unless exact equivalence is proven.

⸻

9.34 Prohibited Hidden Policy

A Translation Definition SHALL NOT contain hidden policy such as:

* preferred providers;
* cost optimization;
* latency optimization;
* quality optimization;
* model ranking;
* runtime routing;
* risk appetite;
* governance reinterpretation;
* objective prioritization;
* supervisory fallback selection;
* content-generation instructions.

Translation rules SHALL be representational only.

Any rule that changes which supervisory action is taken belongs outside Contract 008.

⸻

9.35 Prohibited Runtime Adaptation

A Translation Definition SHALL NOT adapt supervisory meaning based on:

* queue depth;
* endpoint availability;
* current price;
* latency;
* provider congestion;
* model confidence;
* model output;
* historical success;
* current resource pressure;
* user preference not present in committed context.

These may matter to Contract 009 or external deployment systems.

They do not alter translation equivalence.

⸻

9.36 Registry Entry Immutability

A published Translation Definition SHALL be immutable.

Any change to:

* source compatibility;
* target compatibility;
* mapping logic;
* parameter domains;
* numeric behavior;
* ordering;
* atomicity;
* transaction semantics;
* authority rules;
* restriction rules;
* failure conditions;
* proof obligations;

SHALL create a new definition version and hash.

A prior definition SHALL remain resolvable for replay.

Silent in-place edits are prohibited.

⸻

9.38 Definition Deprecation

A Translation Definition MAY be deprecated.

Deprecation SHALL identify:

* deprecation reason;
* replacement definition, if any;
* last valid registry version;
* final supported runtime version;
* replay availability;
* prohibition date or condition.

Deprecated definitions MAY remain valid for deterministic replay.

They SHALL NOT be selected for new translations unless the Committed Translation Configuration explicitly authorizes them.

⸻

9.39 Definition Withdrawal

A Translation Definition MAY be withdrawn when it is proven unsound.

* affected definition versions;
* affected runtime versions;
* affected command types;
* withdrawal reason;
* known impacted artifacts;
* replacement guidance;
* verification evidence.

A withdrawn definition SHALL NOT be used for new translation.

Previously committed artifacts SHALL retain their historical lineage and shall not be silently rewritten.

⸻

9.40 Registry Ownership

Possible authorities MAY include:

* SACS specification authority;

Contract 008 consumes definitions.

It SHALL NOT self-authorize newly generated definitions during canonical translation.

9.44 Multiple Definitions

One translation MAY require multiple Translation Definitions when:

* the Control Command is composite;
* semantic decomposition is required;
* several parameter domains require distinct registered mappings;
* transaction or atomicity wrappers require separate definitions.

Every selected definition SHALL belong to one coherent Translation Profile or an explicitly compatible definition set.

Definition composition SHALL itself be registered or validated through an exact compatibility rule.

Contract 008 SHALL NOT arbitrarily combine individually valid definitions.

⸻

9.45 Definition Compatibility Graph

When multiple definitions are used together, compatibility MAY be represented as a graph:

G_D = (V_D, E_D)

where:

* V_D contains selected Translation Definitions;
* E_D contains declared compatibility, dependency, precedence, and exclusion relations.

The graph SHALL be deterministic and acyclic for dependency relations unless a registered mutually dependent group is defined.

Unresolved conflicts SHALL cause failure.

9.47 Prohibited Registry Practices

Contract 008 SHALL NOT:

* create an ad hoc mapping during translation;
* infer a mapping from parameter names;
* copy a mapping from a different runtime version;
* treat adapter code as canonical definition;
* treat provider documentation as committed definition;
* select an unregistered “close enough” mapping;
* merge incompatible definitions;
* override a known exclusion;
* use a withdrawn definition;
* ignore certificate requirements;
* change precedence after evaluation begins;
* generate a mapping through probabilistic reasoning;
* allow execution success to retroactively validate a definition.

⸻

9.48 Deterministic Resolution

For identical:

* Translation Requirement Set;
* Runtime Capability Evaluation;
* Translation Configuration;
* Translation Registry Snapshot;
* applicable Translation Profiles;
* definition precedence rules;

Contract 008 SHALL resolve the same eligible and selected Translation Definitions.

Formally:

D_t^{*}
=
R_D
\left(
R_t,
E_t^{\mathrm{cap}},
\Gamma_t,
V_t
\right)

where:

* R_t is the Translation Requirement Set;
* E_t^{\mathrm{cap}} is the Runtime Capability Evaluation;
* \Gamma_t is the Committed Translation Configuration;
* V_t is the registry snapshot set;
* D_t^{*} is the selected Translation Definition set.

The resolution function R_D SHALL be deterministic.

9.50 Section 9 Invariant

The governing invariant for the Translation Definition Registry is:

Every canonical translation transformation SHALL be governed by one or more exact, immutable, versioned, hash-addressable, and authorized Translation Definitions. Those definitions SHALL describe representation only, SHALL preserve all source semantics and authority bounds, and SHALL NOT introduce hidden policy, runtime selection, approximation, adaptation, fallback action, or execution authority.
