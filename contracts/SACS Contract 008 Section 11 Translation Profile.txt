11. Translation Profile

11.1 Purpose

This section defines the Translation Profile used by Contract 008.

A Translation Profile is a reusable, immutable specification of one complete translation strategy.

It organizes the Translation Definitions, normalization rules, numeric rules, ordering rules, validation rules, transaction rules, compatibility rules, replay requirements, provenance requirements, and failure rules required to transform a declared class of Committed Control Commands into runtime-specific Inference Commands.

A Translation Profile does not possess cycle authority by itself.

It becomes applicable only when it is:

* identified as the sole root Translation Profile;
* immutably referenced;
* version-bound;
* hash-bound;
* registry-bound;

by the Committed Translation Configuration governing the translation cycle.

The defining identity is:

A Translation Profile is a reusable, immutable specification of one complete translation strategy. It has no cycle authority by itself and becomes applicable only when referenced as the sole root Translation Profile by the Committed Translation Configuration.

⸻

11.2 Architectural Position

The Translation Profile occupies the following position:

Committed Translation Configuration
        ↓ authorizes
Translation Profile
        ↓ organizes
Translation Definitions and Rule Sets
        ↓ govern
Translation Evaluation

The Committed Translation Configuration determines which Translation Profile is authorized.

The Translation Profile determines which definitions and rule families constitute the declared strategy.

The Translation Definitions and rule sets determine the specific transformations and validation requirements.

No lower artifact may replace or reinterpret the root Translation Profile.

⸻

11.3 Profile Authority Boundary

A Translation Profile MAY define:

* supported source Control Command classes;
* supported source semantic classes;
* supported runtime classes;
* required Translation Definitions;
* permitted subordinate profiles;
* normalization strategy;
* numeric strategy;
* ordering strategy;
* validation strategy;
* transaction strategy;
* compatibility strategy;
* replay requirements;
* provenance requirements;
* failure behavior;
* deterministic resolution rules.

A Translation Profile SHALL NOT:

* select itself;
* commit itself to a cycle;
* select a Control Command;
* modify a Control Command;
* select a runtime;
* select a provider;
* redefine Runtime Capability Profile facts;
* authorize execution;
* weaken mandatory restrictions;
* expand supervisory authority;
* generate an unregistered Translation Definition;
* select an alternative profile after failure.

Profile existence is not profile authority.

Profile compatibility is not profile authority.

Profile registration is not profile authority.

Only the Committed Translation Configuration grants cycle authority.

⸻

11.4 Reusable Strategy Specification

A Translation Profile SHALL be reusable across translation cycles only as a definition artifact.

Reuse means that the same immutable profile definition may be referenced by multiple Committed Translation Configurations.

Reuse does not mean that:

* one committed configuration governs several cycles;
* one profile may mutate between cycles;
* prior compatibility applies automatically;
* runtime capability remains unchanged;
* registry snapshots may be refreshed silently;
* a profile may carry authority from one cycle into another.

Each cycle SHALL bind the profile through a distinct Committed Translation Configuration.

⸻

11.6 Root Translation Profile

Every translation cycle SHALL have exactly one root Translation Profile.

The root profile SHALL be identified by the Committed Translation Configuration through:

translation_profile_id
translation_profile_version
translation_profile_hash

The root profile SHALL provide the complete strategy entry point for the translation cycle.

Every subordinate profile, Translation Definition, and rule set used during the cycle SHALL be:

* directly referenced by the root profile; or
* deterministically reachable from it through immutable references.

No second root profile may govern the same translation cycle.

A translation cycle with:

* no root profile;
* multiple root profiles;
* an unresolved root profile;
* a root profile hash mismatch;

SHALL fail.

⸻

11.7 Subordinate Translation Profiles

A root Translation Profile MAY reference subordinate Translation Profiles.

A subordinate profile MAY organize a bounded portion of the strategy, such as:

* one Control Command family;
* one runtime command family;
* one numeric regime;
* one transaction regime;
* one target class;
* one adapter class;
* one semantic decomposition family.

A subordinate profile SHALL:

* have no independent cycle authority;
* be explicitly referenced;
* have exact version and hash bindings;
* declare its scope;
* declare its dependencies;
* declare its exclusions;
* remain within the authority of the root profile.

A subordinate profile SHALL NOT:

* select another root profile;
* override the root profile;
* replace root-level rule sets;
* broaden supported command classes;
* broaden runtime authority;
* introduce unbound definitions;
* change selection precedence.

⸻

11.8 Profile Hierarchy

A Translation Profile hierarchy SHALL be explicit.

The hierarchy MAY be represented as:

[
G_P = (V_P,E_P)
]

where:

* (V_P) is the set of Translation Profiles;
* (E_P) is the set of explicit profile-reference relations.

The hierarchy SHALL have:

* exactly one root;
* deterministic traversal;
* explicit dependency relations;
* no unresolved conflicts;
* no unauthorized cycles.

Profile-reference cycles SHALL be prohibited unless a later registered model explicitly defines a valid mutually bound profile group.

In the absence of such a model, the profile graph SHALL be acyclic.

⸻

11.12 Runtime Scope

The runtime target remains fixed by the governing configuration and referenced Runtime Capability Profile.

1. an exact Translation Definition set; or
2. a deterministic Translation Definition resolution model.

translation_definition_ids

11.16 Normalization Strategy

The profile SHALL identify the normalization strategy applicable to its Translation Definitions.

The normalization strategy SHALL specify which classes of representation-preserving transformations are permitted.

It SHALL NOT authorize:

* semantic approximation;
* unsupported-value weakening;
* automatic clipping;
* target substitution;
* scope substitution;
* authority expansion;
* omission of mandatory restrictions.

The specific normalization mechanics belong to Section 13.

The profile SHALL NOT select a more permissive Numeric Profile after incompatibility.

11.21 Compatibility Strategy

The profile SHALL bind one exact compatibility rule set.

The compatibility strategy SHALL define how later evaluation determines whether the profile and its dependencies are compatible with:

* the Committed Control Command;
* the Translation Requirement Set;
* the Runtime Capability Profile;
* the Numeric Profile;
* the registry snapshot set;
* the implementation capability profile.

The compatibility strategy SHALL NOT:

* redefine runtime capabilities;
* waive unsupported requirements;
* remove known exclusions;
* authorize partial translation;
* select another profile.

11.24 Preconditions

11.25 Postconditions

A Translation Profile SHALL declare the postconditions its successful application is intended to establish.

Postconditions MAY include:

* complete Translation Definition resolution;
* complete requirement coverage;
* deterministic normalized parameter representation;
* complete ordering representation;
* complete transaction representation;
* complete validation-obligation construction;
* complete provenance construction.

Profile postconditions describe expected strategy results.

They do not certify that those results were achieved.

Certification belongs to later validation stages.

⸻

11.26 Profile Closure

The complete dependency closure of a Translation Profile SHALL be deterministically resolvable.

Let:

[
\operatorname{Closure}(P)
]

denote all artifacts reachable from Translation Profile (P).

The closure MAY include:

* subordinate profiles;
* Translation Definitions;
* normalization rules;
* numeric rules;
* ordering rules;
* validation rules;
* transaction rules;
* compatibility rules;
* replay policies;
* provenance profiles.

Every artifact in the closure SHALL have:

* an identifier;
* a version;
* a hash;
* an immutable registry or embedded-definition binding.

The profile closure SHALL NOT depend on:

* ambient configuration;
* implementation-local defaults;
* current registry state;
* provider documentation;
* live runtime discovery.

⸻

11.27 Profile Closure Versus Configuration Closure

Translation Profile closure and Committed Translation Configuration closure are related but distinct.

Profile closure answers:

Which artifacts constitute this reusable strategy?

Configuration closure answers:

Which artifacts are authorized for this exact cycle?

Therefore:

[
\operatorname{Closure}(P_t)
\subseteq
\operatorname{Closure}(\Gamma_t)
]

where:

* (P_t) is the root Translation Profile;
* (\Gamma_t) is the Committed Translation Configuration.

The governing configuration MAY further bind:

* exact registry snapshots;
* exact command identity;
* exact Runtime Capability Profile;
* selection authority;
* commitment evidence;
* cycle-specific replay and provenance requirements.

A profile artifact outside configuration closure is unauthorized for the cycle.

⸻

11.28 Profile Immutability

A published Translation Profile SHALL be immutable.

Any change to:

* supported source classes;
* supported runtime classes;
* Translation Definitions;
* subordinate profiles;
* rule sets;
* resolution logic;
* dependencies;
* exclusions;
* preconditions;
* postconditions;
* failure behavior;

SHALL create a new profile version and artifact hash.

A prior profile version SHALL remain resolvable for replay.

Silent in-place modification is prohibited.

⸻

11.29 Profile Versioning

Translation Profiles SHALL use semantic versioning.

A major version change indicates a breaking change to:

* strategy semantics;
* supported command scope;
* runtime scope;
* rule-set organization;
* definition resolution;
* authority-preservation behavior;
* validation behavior.

A minor version MAY add backward-compatible:

* command classes;
* definitions;
* rule references;
* optional subordinate profiles;
* validation capabilities.

A patch version MAY clarify non-semantic defects.

Compatibility across profile versions SHALL be explicit.

Silent profile migration is prohibited.

⸻

A deprecated profile SHALL not be selected for a new Committed Translation Configuration unless the selection policy explicitly permits it.

Deprecation does not alter prior committed configurations.

* affected Translation Definitions;
* affected runtime scopes;
* affected rule sets;
* withdrawal reason;
* known impacted configurations;
* replacement guidance;
* supporting evidence.

A withdrawn profile SHALL NOT govern new translation cycles.

Previously committed artifacts SHALL retain historical lineage.

They SHALL NOT be silently rewritten.

11.34 Profile Resolution

The root Translation Profile SHALL be resolved directly from the Committed Translation Configuration.

Resolution SHALL include validation of:

translation_profile_id
translation_profile_version
translation_profile_hash
translation_profile_registry_snapshot_id

Contract 008 SHALL NOT search for a substitute profile.

Resolution SHALL produce one of:

TRANSLATION_PROFILE_RESOLVED
TRANSLATION_PROFILE_MISSING
TRANSLATION_PROFILE_HASH_MISMATCH
TRANSLATION_PROFILE_WITHDRAWN
TRANSLATION_PROFILE_RESOLUTION_FAILURE

Only TRANSLATION_PROFILE_RESOLVED permits later profile-conformance evaluation.

⸻

11.35 Subordinate Profile Resolution

Subordinate profiles SHALL be resolved through the root profile’s immutable dependency graph.

Resolution SHALL be deterministic.

For each subordinate profile, Contract 008 SHALL verify:

* identifier;
* version;
* hash;
* scope;
* dependency relation;
* registry snapshot;
* exclusion status;
* withdrawal status.

A missing or ambiguous subordinate profile SHALL cause profile-resolution failure.

Contract 008 SHALL NOT omit a mandatory subordinate profile.

⸻

11.36 Profile Applicability

Profile resolution does not establish profile applicability.

The profile may resolve correctly but still be incompatible with:

* the Committed Control Command;
* the Translation Requirement Set;
* the Runtime Capability Profile;
* the Numeric Profile;
* the target;
* the registry snapshot set.

Therefore:

Translation Profile Resolution
≠
Validated Translation Binding

Profile applicability SHALL be proven later through:

Translation Configuration Conformance
Translation Compatibility Evaluation
Validated Translation Binding

⸻

11.37 Deterministic Profile Environment

For identical:

* Committed Translation Configuration;
* root Translation Profile;
* profile registry snapshot;
* subordinate profile graph;
* profile dependency definitions;

a conforming implementation SHALL resolve the same profile closure.

Formally:

[
C_P

\operatorname{ResolveProfileClosure}
\left(
P,
V_P
\right)
]

where:

* (P) is the root Translation Profile;
* (V_P) is the bound profile registry snapshot;
* (C_P) is the resolved profile closure.

The resolution function SHALL be deterministic.

Probabilistic profile resolution is prohibited.

⸻

11.38 Profile Failure Behavior

A Translation Profile SHALL define failure behavior for:

* missing definitions;
* unresolved subordinate profiles;
* hash mismatches;
* dependency failures;
* exclusion matches;
* unsupported source classes;
* unsupported runtime classes;
* ambiguous resolution;
* invalid rule-set references;
* incompatible profile composition;
* certification failure.

Profile failure behavior SHALL remain fail-closed.

A profile SHALL NOT authorize fallback to:

* another profile;
* another runtime;
* another provider;
* weaker normalization;
* relaxed numeric semantics;
* reduced validation;
* best-effort transaction behavior.

11.40 Prohibited Profile Practices

Contract 008 SHALL NOT:

* create a profile during translation;
* modify a profile during translation;
* select a profile not bound by the configuration;
* replace the root profile after failure;
* combine multiple root profiles;
* infer profile scope from implementation behavior;
* infer profile compatibility from prior success;
* search for a “close enough” profile;
* merge definitions from unrelated profiles;
* resolve profile dependencies from mutable registries;
* override profile exclusions;
* skip mandatory subordinate profiles;
* ignore certification requirements;
* permit implementation-local profile extensions;
* treat a profile as runtime capability authority;
* treat a profile as execution authority.

⸻

⸻

11.42 Profile Composition

A root profile MAY compose subordinate profiles only through an explicit Profile Composition Definition.

A Profile Composition Definition SHALL specify:

profile_composition_definition_id

⸻

11.43 Conflict Resolution

A Translation Profile SHALL define deterministic conflict behavior.

Possible conflicts include:

* two definitions matching the same predicate;
* two rule sets governing the same field;
* incompatible numeric requirements;
* inconsistent ordering models;
* inconsistent transaction requirements;
* overlapping subordinate-profile scopes.

Conflict resolution SHALL be:

* explicitly defined;
* deterministic;
* non-expansive;
* hash-bound;
* within configuration authority.

If no exact conflict rule exists, the conflict SHALL cause failure.

⸻

11.44 Profile Completeness

A Translation Profile is complete when its immutable closure defines or references every strategy category required by its declared scope.

Completeness requires, where applicable:

* source scope;
* runtime scope;
* Translation Definitions;
* normalization strategy;
* numeric strategy;
* ordering strategy;
* validation strategy;
* transaction strategy;
* compatibility strategy;
* replay policy;
* provenance requirements;
* failure behavior.

A profile that omits a mandatory strategy category SHALL be incomplete.

Profile completeness does not establish runtime compatibility.

⸻

11.45 Profile Non-Authority

A Translation Profile SHALL remain noncanonical with respect to cycle authority.

Even when a profile is:

* valid;
* complete;
* certified;
* compatible;
* present in the registry;

it SHALL NOT govern a cycle unless the Committed Translation Configuration binds it as the sole root profile.

This preserves the distinction:

Registry presence
    means the strategy exists.
Profile validity
    means the strategy is internally coherent.
Profile compatibility
    means the strategy may apply.
Configuration commitment
    means the strategy is authorized for the cycle.

⸻

11.46 Section 11 Artifact Flow

Committed Translation Configuration
        ↓
Root Translation Profile Reference
        ↓
Profile Identity and Hash Resolution
        ↓
Profile Registry Snapshot Resolution
        ↓
Subordinate Profile Resolution
        ↓
Dependency and Exclusion Resolution
        ↓

        ↓

        ↓

        or
Translation Profile Failure

At the conclusion of Section 11:

* the complete reusable strategy specification is resolved;
* the root profile and subordinate profile hierarchy are known;
* the authorized definition and rule-set organization is known;
* no Translation Configuration Conformance result exists;
* no Translation Compatibility result exists;
* no Validated Translation Binding exists;
* no Translation Evaluation has occurred;
* no Proposed Inference Command Set exists.

⸻

11.47 Fundamental Translation Profile Invariant

Every translation cycle SHALL have exactly one root Translation Profile bound by the Committed Translation Configuration.

The root Translation Profile SHALL define one complete, immutable, deterministic translation strategy through exact references to:

* Translation Definitions;
* subordinate profiles;
* normalization rules;
* numeric rules;
* ordering rules;
* validation rules;
* transaction rules;
* compatibility rules;
* replay requirements;
* provenance requirements;
* failure rules.

The profile and every artifact in its closure SHALL be immutable, versioned, hash-bound, and reachable through the Committed Translation Configuration.

A Translation Profile SHALL possess no cycle authority by itself.

Contract 008 SHALL NOT create, select, modify, merge, negotiate, repair, replace, or supplement the root Translation Profile.

When the profile is missing, incomplete, ambiguous, incompatible, withdrawn, or unresolved, Contract 008 SHALL produce an explicit Inference Translation Failure and no canonical Inference Command Set.
